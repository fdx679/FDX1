# Vibe Coding 方法学习笔记

> 本笔记是课程设计第 1 阶段（vibe coding 方法学习）的产出，记录在本课程设计项目中使用 AI 编程工具的方法论与实践要点。所有方法均已在本项目实际应用（见各阶段记录）。

---

## 一、提示词工程（Prompt Engineering）

提示词是人与 AI 之间的"需求说明书"，写好提示词是 vibe coding 的第一步。本项目遵循 **任务拆解 → 约束说明 → 验收标准** 三段式结构。

### 1. 任务拆解（Task Decomposition）

复杂任务拆解为 AI 可逐条执行的子任务，避免一次性给出模糊大目标。

| 错误示范 | 正确示范 |
|----------|----------|
| "帮我做个招聘系统" | "为课程设计实现简历技能抽取模块：输入简历文本，输出技能列表" |
| "优化一下代码" | "修复 resume_parser.py 中姓名正则大小写敏感问题：NAME: 大写开头无法匹配" |

**本项目实践**：系统开发拆解为"技能词表 → 技能抽取 → 简历解析 → 分类器 → 知识图谱 → 匹配器 → 数据库 → API → 前端 → 测试"十个模块逐一实现。

### 2. 约束说明（Constraints）

显式说明边界条件，防止 AI 过度设计或跑偏：

- **技术栈约束**："使用 Flask + SQLite + scikit-learn，不用 Django / MySQL / BERT（本地无法下载模型）"
- **运行环境约束**："必须在无外网环境下可运行，ECharts 需本地化，模型需本地训练"
- **数据约束**："隐私信息必须掩码，不得入库真实邮箱/电话"
- **范围约束**："只改 resume_parser.py，不动其他文件"

### 3. 验收标准（Acceptance Criteria）

给 AI 可验证的完成标准，避免"差不多就行"：

- "分类器在测试集准确率 ≥ 50%（25 类多分类，随机基线 4%）"
- "自动化测试 pytest 全部通过"
- "简历解析：姓名/学历/经验/技能字段均正确提取"

## 二、上下文工程（Context Engineering）

上下文决定 AI 的"记忆"，上下文工程让 AI 在正确上下文下工作。

### 1. 项目规则文件

在项目根目录维护规则文件，让 AI 每次进入项目都能快速对齐：

- `README.md`：项目总览、目录结构、运行方式（本项目已维护）
- `data/README.md`：数据来源与处理规范（本项目已维护）
- `prompt/conversation_log.json`：AI 交流记录（本项目的"过程档案"）
- `docs/`：设计文档（本项目已维护）

### 2. 让 AI 先读代码再改（Read Before Edit）

**关键原则**：AI 改代码前必须先读目标文件和相关依赖，不能凭空修改。

**本项目实践**：在修复 `resume_parser.py` 姓名正则时，先读取文件定位 bug（正则大小写敏感、匹配过度），再针对性修改，并用测试验证，而不是让 AI 凭记忆重写整个文件。

```
修改前：读取目标文件 → 理解现有实现 → 定位具体行
修改中：最小改动（只改有问题的正则/逻辑）
修改后：运行相关测试 → 确认无回归
```

## 三、规格驱动开发（Specification-Driven Development）

流程：**需求文档 → AI 制定计划 → 分步实现 → 逐步验收**。

### 1. 需求文档先行

本项目以 `docs/需求规格说明书.md` 作为开发依据，明确功能需求、数据需求、非功能需求。

### 2. AI 制定计划

根据需求文档，AI 输出分步实施计划（里程碑）：

| 里程碑 | 内容 | 验收 |
|--------|------|------|
| M1 数据准备 | 数据集收集/清洗/入库 | data/ 目录文件齐全，README 说明 |
| M2 算法模块 | 解析/分类/匹配/图谱 | 单测通过 |
| M3 后端服务 | Flask API | API 集成测试通过 |
| M4 前端界面 | 演示页面 | 页面可访问、API 连通 |
| M5 测试与集成 | pytest 全量 | 23 项测试全通过 |

### 3. 分步实现 + 逐步验收

每完成一个模块立即验证（写测试 → 运行 → 修复），不累积到后期统一排查。本项目中，分类器 `multi_class` 参数错误、姓名正则匹配过度等 bug 均在当步发现并修复，避免问题堆积。

## 四、AI 代码的自动化测试与人工审查

### 1. 自动化测试（必备）

- 使用 pytest 编写单元测试与集成测试
- **每个算法模块**：解析、分类、匹配、图谱均有独立测试
- **API 层**：用 Flask test client 测试所有接口（含异常分支）
- 回归保护：修改后全量运行 `pytest tests/`，确保 23 项全通过

### 2. 人工审查（必做）

AI 生成的代码**不能直接信任**，须人工审查关键逻辑：

- 数据合规：隐私掩码是否生效（本项目验证：0 残留邮箱）
- 业务逻辑：匹配评分公式是否合理（本项目发现软技能导致区分度不足，人工调整）
- 安全性：避免注入等风险（本项目 API 使用 JSON 输入校验）
- 可解释性：输出缺失技能提示，供答辩讲解

**本项目 AI 出错案例**：

| 问题 | AI 初始实现 | 人工审查发现 | 修正 |
|------|-------------|--------------|------|
| 分类器 API 兼容 | 使用 `multi_class` 参数 | 新版 sklearn 已移除，运行时 TypeError | 移除参数 |
| 姓名提取过度 | 正则吞入后续文本 | 输出 "Li Ming. Python" | 限定字母词、标点停止 |
| 匹配区分度低 | 软技能计入覆盖率 | HR/Sales 等岗位虚高 | 硬技能+规模惩罚 |

## 五、调试与人工接管策略

### 1. 回滚（Rollback）

git 全程版本管理，出问题可回退：

```bash
git log --oneline        # 查看提交历史
git checkout -- 文件      # 丢弃单个文件未提交改动
git reset --hard <commit> # 回退到某提交
```

### 2. 缩小改动（Minimal Change）

- 一次只改一个功能点，不混入无关重构
- 修改前记录当前状态，修改后立即测试
- 保持提交粒度小、说明有意义（本项目的 git 提交均按阶段拆分）

### 3. 最小复现（Minimal Reproduction）

调试时构造最小复现用例，定位问题根因：

```python
# 最小复现：姓名正则 bug
def test_name_issue():
    r = parse_resume("Name: Li Ming. Python Developer")
    assert r["name"] == "Li Ming"   # 初始实现返回 "Li Ming. Python"
```

- 先构造能稳定复现 bug 的最小输入
- 定位到具体函数与正则
- 修复后再跑全量测试防回归

### 4. 人工接管时机

遇到以下情况应人工接管（而非继续让 AI 盲试）：

- AI 连续 2 次修复无效 → 人工阅读源码定位根因
- 涉及数据合规/安全 → 人工审查确认
- 评分/权重等业务参数 → 人工结合实际语义调整

## 六、Git 版本控制（代码管理）

本项目全程使用 git 管理，小步提交、说明有意义：

```bash
git init                          # 初始化
git add <file>                    # 暂存
git commit -m "feat: 完成XXX模块"  # 语义化提交
git push origin main              # 推送远程
```

提交信息规范（本项目实践）：

| 类型 | 示例 |
|------|------|
| feat（新功能） | `feat: 完成数据准备与预处理` |
| fix（修复） | `fix: 修复姓名提取正则匹配过度` |
| test（测试） | `test: 新增匹配器单元测试` |
| docs（文档） | `docs: 新增需求规格说明书` |

## 七、项目实践总结

在本课程设计中，vibe coding 方法已全程应用：

1. **提示词工程**：每项任务按"拆解-约束-验收"组织，数据、算法、后端、前端分步实现
2. **上下文工程**：维护 README/data README/prompt 日志等规则文件；修改前先读代码
3. **规格驱动开发**：以需求规格说明书为纲，按里程碑分步实现、逐步验收
4. **自动化测试**：pytest 23 项测试覆盖全部模块，回归保护
5. **人工审查**：审查并修复了 sklearn 兼容、正则精度、匹配区分度等 3 类 AI 出错问题
6. **调试接管**：运用最小复现定位 bug，git 版本管理保障可回滚
